# Evaluation corpus — build and measure

The corpus is generated by the **normal pipeline**, stored on Drive, and recorded
in its **own database table**. Nothing here touches user data: no history row, no
saved design, and no user-facing statistic on `/evaluation` changes.

## Layout (Google Drive)

```
MyDrive/DarDesign/evaluation/
  inputs/                 the test rooms — put your photos here
  finals/lebanese/        raw LoRA output, one per room
  finals/khaleeji/
  finals/moroccan/
  baselines/              prompt-only, for the LoRA-vs-baseline ablation
  results/                results.csv, summary.md, confusion_matrix.png, metrics_bars.png
```

## 0. Put the inputs in place — do this first

Nothing can run without test rooms. Copy 10–15 room photos into
`MyDrive/DarDesign/evaluation/inputs/` (or `data/eval_rooms/` locally). Use rooms
that are **not** in `datasets/*/images` — measuring on the images a LoRA trained
on would flatter the result and an examiner will ask.

Filenames become the room id, so keep them simple: `room_01.jpg`, `room_02.jpg`.

## 1. Generate — Colab, GPU, ~1–2 min per image

```bash
DRIVE=/content/drive/MyDrive/DarDesign/evaluation

python scripts/generate_finals.py \
    --rooms-dir $DRIVE/inputs --out $DRIVE/finals --by-culture --limit 15

python scripts/generate_finals.py \
    --rooms-dir $DRIVE/inputs --out $DRIVE/baselines --no-lora --limit 15
```

15 rooms x 3 cultures = 45 images per set. Existing files are **skipped**, so a
disconnected runtime resumes where it stopped — just run it again.

Output is **raw pipeline PNG**: never upscale or post-process these. SSIM and
LPIPS compare against the input pixel-for-pixel, and an upscaled image would
report a structure score that is an artefact of the upscaler.

## 2. Measure — Colab, same session

```bash
pip install -q lpips open_clip_torch

python eval/run_metrics.py \
    --inputs $DRIVE/inputs \
    --outputs $DRIVE/finals \
    --baselines $DRIVE/baselines \
    --out $DRIVE/results
```

Writes `results.csv`, `summary.md`, `confusion_matrix.png` and `metrics_bars.png`
straight to Drive, so they survive the session ending.

## 3. Load into the database — on the machine that owns it

The metrics run on the disposable GPU box; the database lives on your laptop.
Copy `results/results.csv` down, then:

```bash
python eval/run_metrics.py --import-csv eval/results.csv --db backend/dardesign.db
```

That upserts into `evaluation_results`, keyed on (room, culture, set) — re-running
the suite updates rows rather than stacking duplicates, so the averages cannot
drift upward each time.

(If the database is reachable from the run itself, `--db` on step 2 does the same
thing in one pass.)

## 4. Show it on the dashboard

`/evaluation` reads `eval/results.csv`. Drop the file there and the Automatic
metrics section fills in — no code change:

```bash
copy results.csv eval\results.csv
```

## What is kept separate, and how

| | |
|---|---|
| `evaluation_results` table | Its own table. No foreign key to users or history. |
| Rooms generated / average time | Read from `history`. Evaluation never writes there, so these are untouched. |
| Most-used culture, ratings | Read from `history` / `feedback`. Untouched. |
| Generation behaviour | `generate_finals.py` calls `transform_room` directly. The website's flow is not involved. |
